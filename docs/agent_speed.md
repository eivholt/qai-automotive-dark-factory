# IQ9 agent latency study

The subsequent [Ministral comparison](ministral_controller.md) replaces the
default controller. This page preserves the earlier Qwen measurements.

19 September 2026. This follows the successful compiled Reason2 deployment and
examines the remaining Qwen controller bottleneck. Private evidence is under
`artifacts/agent-speed-20260919/`; weights and generated files stay ignored.

## Lessons from the earlier tutorials

The [OR deployment](https://github.com/eivholt/or-edge-agent/blob/main/IQ9_EVK.md)
and [shipping tutorial](https://github.com/eivholt/qai-nemotron/blob/main/tutorial_build_agentic_shipping_iq9075.md)
use persistent native services with the model's own tool template and parser.
Our Qwen server already does this, with thinking disabled and greedy decoding.
There is no per-request model loading to remove. The shipping model's reported
roughly 5 generated tokens/s does not establish that replacing Qwen with that
Ministral NPU export would accelerate this application.

Text-controller conversation caching is separate from camera inference. The OR
tutorial documents stale visual-token reuse in its VLM path. Our Reason2 worker
continues to reset its KV state for every new image batch; no image-result cache
was introduced to obtain these speed measurements.

The [agentic models tutorial](https://github.com/eivholt/qai-nemotron/blob/main/tutorial_agentic_models_iq9075.md)
and [comparison](https://github.com/eivholt/qai-nemotron/blob/main/docs/benchmarks/model_coverage_and_agentic_comparison_20260716.md)
emphasize deployed template/parser correctness and completed-task evaluation.
Their Ornith CPU thread experiment is particularly relevant: Ornith uses Qwen3.5
hybrid attention, and IQ9 has eight Cortex-A78C cores. Qwen3's conventional
compiled exporter is not a substitute for Qwen3.5 recurrent-state support.
The locally installed QAI Hub Qwen3.5-2B recipe selects `geniex_llamacpp`, not a
compiled QAIRT graph; it is not evidence of a compiled 9B path.

Parallel tool reads do not directly fit these camera jobs: one physical arm
visits the requested poses, and mechanical jobs share the cell. Preserve the
serial executor and agent-selected jobs. Do not copy another demo's ordered
policy enforcement into this agent mode.

## Changes

- Use eight CPU threads for Qwen prefill and decoding, keeping the exact Q4_K_M
  weights and sampling unchanged.
- Keep complete assistant/tool history, but omit duplicated tool/argument names,
  inference-duration diagnostics, image count and the generic successful
  `model_classification` reason from model-facing results. Keep decisions,
  validity, specific errors, stage, holder state and observation clocks.
- Serialize those clocks as numeric seconds to three decimal places. The full
  precision journal and eight-second Reason2 freshness check are unchanged.
  This avoids tokenizing meaningless 17-digit floating-point tails.
- Clarify the existing preassembled-body acceptance criterion in the prompt:
  initial presence G supplies visual acceptance; both thermal gates still need
  G, while the post-welding seating check is for panels assembled in this cell.
  Tools remain available and the executor adds no recipe veto.

No acceptance rule, recipe veto, ground-truth input or next-action selection is
added. HUD reasons remain generated by Qwen. Inspections remain unchanged.

## Fixed-history results

Both EVK runs use eight threads and the same ten saved decision points. Excluding
each run's first request, compact messages reduce median HTTP time from
**13.281 s to 10.985 s (17.3%)**, and median newly evaluated prompt tokens from
128 to 74. This measures compaction separately from the thread change. The cold
original first request took 74.335 s; the compact run reused the loaded service
and policy cache, so its first request is not a cold-start comparison.

Original history matched all ten reference choices; compact history matched
nine. The difference was choosing seating inspection before weld cooling after
welding, which the task permits. Neither run measures fresh classification or
closed-loop completion. Host screening likewise matched 9/10 original and 10/10
compact; do not interpret those small differences as an accuracy improvement.

All four subsequent EVK synthetic fault probes returned appropriate choices:
15-second waits for hot sealant and hot welds, hold for defective seating, and
another presence inspection after an invalid stale result. This is four bounded
decision checks with simulated observations, not a sensor accuracy evaluation.

## Closed-loop follow-up

The first full run completed one body, then held on the preassembled body after
Qwen unnecessarily requested seating inspection three times, each returning A.
The controller respected uncertainty; this failed completion test is retained in
`evk-process-smoke/`. It exposes a limitation of an optional inspection outside
the intended post-welding workflow, not a new held-out classifier result.

The final prompt separates the already-existing acceptance criteria for initially
present and newly assembled panels. It does not choose the next tool in code or
ignore an observed A. Host screening of the clarification passed all four
preassembled decision points and all four fault probes. The saved assembly
history differed on two useful choices: seating before weld cooling, and release
without a redundant second sealant inspection. These are development probes;
the actual EVK/Unreal run must establish completed behavior.

The final actual run **passed** assembly/preassembled/assembly in **484.345 wall
seconds**, with **22 Qwen choices, 11/11 fresh valid Reason2 batches, no rejected
commands and zero independent audit failures**. All three bodies departed.
The preassembled body used only presence and both thermal inspections. Each
newly assembled body used the required sealant, placement, cooling, welding,
seating, weld-cooling and release jobs. No ground-truth fields reached a model.

| Full live EVK run | Previous | Optimized |
|---|---:|---:|
| Agent decision median | 15.369 s | 11.186 s |
| Reason2 batch median | 4.847 s | 1.415 s |
| Three-body wall time | 648.77 s | 484.35 s |
| Agent choices / camera batches | 25 / 14 | 22 / 11 |

The overall 25.3% wall-time reduction includes the earlier Reason2 NPU upgrade,
CPU threading, compact results and avoiding redundant inspections. It is not an
isolated compaction measurement; the fixed-history comparison above isolates
that more closely. The new prompt required **77.712 s for the first decision**;
do not describe startup as an 11-second operation. This remains three-body
development integration, not new held-out accuracy.

`verify_live_agent.py` passed, as did 2,144 physical-camera telemetry checks,
137 native policy checks and 156 Python tests. The policy fixture explicitly
preserves invalid evidence and full-precision diagnostic clocks after compaction.
About 17.1 GiB remained available with all three models resident, with no service
restarts observed. The final welding capture was reviewed and displayed in chat.
Unreal and the temporary host controller are closed; the EVK services remain up.
After that run, all four fault probes were repeated on the EVK with the final
prompt and passed: wait15 / wait15 / hold / inspect presence. The fault-probe
latencies include jumps between different history prefixes and are not normal
consecutive live-turn timing measurements.

## Rejected Hexagon candidate

A separate offline Q8_0 conversion of the existing Q4_K_M file tested supported
Hexagon matrix types. This is requantization, not a full-precision source export,
and would need new decision validation even if it loaded. Original weights remain
untouched. The candidate failed before inference with a FastRPC mapping error
at a 1,062,424,576-byte allocation. A second run set `GGML_HEXAGON_MBUF=256` and
put `output.weight` on CPU; it also failed, at 232,194,048 bytes. Roughly 22 GiB
of system RAM was available. This is a device mapping failure, not an accuracy
result or proof of insufficient physical RAM. Do not enable it in live startup.
The working QAIRT Reason2 workers stayed loaded.

The EVK initially lacked disk space for the candidate. Three duplicate transfer
archives were removed after their SHA-256 matched retained workstation copies.
Extracted bundles, active models and validation reports were kept.
The rejected Q8 candidate was removed from the EVK after preserving its hash,
conversion source and startup logs; the workstation copy remains available.

## Reproduce fixed-history replay

`scripts/agent/replay_latency.py` reads only saved model-facing messages/tools,
then submits each prefix. Expected calls stay evaluator-only. It records raw
replies, usage, llama.cpp timings and HTTP time. Agreement is not closed-loop
accuracy: a different useful inspection can also satisfy the objective.

```bash
python3 scripts/agent/replay_latency.py \
  --runtime artifacts/agent-live-20260918/evk-timeout-fixed/process_runtime.json \
  --endpoint http://127.0.0.1:18195/v1/chat/completions \
  --output artifacts/agent-speed-20260919/original.json
# Repeat with --compact and a distinct --output path.
```

Wait for `/health` and avoid competing clients. Report cold first-request time
separately from subsequent cache-assisted calls. The actual Unreal check uses
`-ProcessSmoke -ProcessControl agent -Enhancements` with the EVK endpoints in
[live agent control](live_agent_control.md). Its audit observes wrong choices
without vetoing or repairing them.

Use `--compact --fault-probes` for four separate synthetic last-observation
checks: hot sealant, hot welds, defective seating and invalid presence evidence.
These expect waiting/inspection/hold instead of an action, and specifically hold
for a seating defect. They execute no physical jobs and do not validate Reason2.
