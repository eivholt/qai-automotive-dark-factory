# One-token Ministral controller — 19 September 2026

The unmodified Ministral-3-3B-Instruct-2512 Q4_K_M can choose a high-level factory
action with **one output token, without fine-tuning**. A small loopback protocol
adapter converts that token into the existing Unreal tool call. Reason2 and its
two vision adapters are unchanged. See [live agent control](live_agent_control.md)
for physical execution and observation boundaries.

## How selection works

`scripts/agent/single_token.py` derives a separate prompt from
`configs/live_agent.json`: it retains the task, inspection meanings and acceptance
criteria, replaces the JSON/reason output instruction, and appends this fixed menu:

| Code | Tool |
|---|---|
| A | Inspect panel presence |
| B | Apply sealant |
| C | Pick/place/hold the panel |
| D | Inspect sealant temperature |
| E | Weld the panel |
| F | Inspect panel seating |
| G | Inspect weld temperature |
| H | Release/retract holder |
| I | Send body forward |
| J / K / L | Wait 1 / 5 / 15 seconds |
| M | Hold for operator attention |

All 13 actions remain available on every turn. There is no state-dependent
action mask, recipe veto or fallback controller. These action letters are
separate from Reason2's G/R/A observation labels.

The adapter verifies that A–M are unique single tokens (IDs 1065–1077 for the
tested tokenizer), applies the native chat template, and requests one token
with temperature zero and the temperature sampler. It reads the unmasked,
pre-sampling top-128 log probabilities and requires the global highest-scoring
token to be one of the action codes. No grammar or logit bias forces a choice.
A non-action winner or malformed result returns an error; it does not silently
select the best remaining action. This is next-token argmax selection, not a
nearest-embedding search.

Only top-128 scores are returned, not the full vocabulary. Omitted action
probabilities are reported as unknown, with bounds on total action probability
mass. We do not normalize a forced choice into artificial confidence, or apply
Reason2's trained vision thresholds to this untrained controller.

Completed assistant calls become their actual action codes in model history;
their real tool results become following user messages. Body arrival starts a
new history. Unsupported historical wait durations are rejected rather than
rounded. No expected actions, source faults, temperatures or audit feedback enter
this transformation. The discrete waits are a deliberate limitation of this
protocol; the original tool-call endpoint still supports variable waits.

The JSON envelope and HUD reason are generated by protocol code. The reason
explicitly says `Selected action code X; no generated explanation`. The model
does **not** generate a rationale. Request/body/pause epochs, mechanical arm
clearance and the independent post-action audit remain owned by Unreal.

## Startup

On the prepared EVK, the existing stack launcher now starts both the native
Ministral service on 18195 and the protocol adapter on 18196. It only starts the
one-token adapter for Ministral; selecting Qwen stops that adapter.

```powershell
wsl.exe ssh ubuntu@192.168.1.158 bash /home/ubuntu/qai-dark-factory/repo/scripts/model/start_evk_qairt.sh --agent
wsl.exe bash scripts/model/start_evk_tunnel.sh --agent
.\unreal\Scripts\run.ps1 -Process -ProcessControl agent -Enhancements `
  -AgentEndpoint http://127.0.0.1:18196/v1/chat/completions `
  -ProcessEndpoint http://127.0.0.1:18198/v1/inspect -ProcessModelSource evk_hexagon
```

Wait for the adapter's `/health` to respond after starting it. This endpoint
reports adapter liveness and startup tokenizer verification; backend failures
still surface on inference. Port 18195 remains the original native tool-call
endpoint with generated short reasons. Use only one controller endpoint at a
time: both share the same model and prompt-cache slot. No Unreal endpoint default
or flow-controller default changed.

For host GPU experiments, start the existing host services from the live-agent
guide, then run this in another WSL terminal:

```bash
DF_SINGLE_TOKEN_BACKEND=http://127.0.0.1:18193 DF_SINGLE_TOKEN_PORT=18194 \
  bash scripts/agent/start_single_token.sh
```

Select `-AgentEndpoint http://127.0.0.1:18194/v1/chat/completions` in Unreal.
The adapter uses Python's standard library. Its HTTP listener is loopback-only,
request/history sizes are bounded, and only one request runs at a time. Normal
runs save no adapter request files. Optional `--qa-log-dir` must be empty and
saves at most 64 requests; all such outputs remain private.

## Development checks and limits

Host GPU and EVK each passed 9/9 assembly, 4/4 preassembled, 4/4 fault and 16/16
varied preassembled-history probes. Continued replay uses actual preceding model
choices and stops on a mismatch before attaching a saved result to the wrong
action. Fault probes cover hot sealant, hot weld, defective seating and invalid
presence. These probes execute no physical jobs and are not held-out accuracy.

The first actual cold EVK run completed assembly/preassembled/assembly in
197.913 seconds, with 24 one-token choices, 12 Reason2 batches, zero rejected
calls and zero audit failures. An ambiguous sealant result on the preassembled
body caused a model-selected wait and reinspection; it still performed the
independent weld inspection. Median controller latency was 1.593 s, first
decision 17.802 s, and Reason2 median 1.415 s. All 24 raw token winners matched
dispatched jobs; the physical-camera verifier passed 2,338 checks.

A second clean model restart on the normal EVK service passed again:

| Actual EVK integration | Native tool calls | One-token final run |
|---|---:|---:|
| Three bodies | 253.539 s | **198.266 s** |
| Median controller decision | 3.991 s | **1.607 s** |
| First decision after restart | 28.586 s | **18.036 s** |
| Median Reason2 batch | 1.415 s | 1.432 s |
| Controller choices / camera batches | 22 / 11 | 24 / 12 |
| Rejected calls / audit failures | 0 / 0 | 0 / 0 |

The final run is 21.8% faster overall and its median controller decision is 59.7%
faster. Both one-token runs handled ambiguous sealant by waiting and reinspecting,
then obtained a separate weld result before departure. Their combined 48 actions
matched the recorded raw winners, prior dispatched actions and actual tool
observations. Each passed 2,338 physical-camera checks. Minimum raw winning-token
probability was 0.500 in the first run and 0.608 in the second; those are not
calibrated correctness estimates. All 169 Python tests pass. Deliberately altered
observation, prior-action and current-choice logs were rejected by the audit.

The final private evidence is `evk-final-cold-process` with `proxy-final-cold`.
Unreal and temporary candidate/host services are closed; normal EVK services and
tunnels remain ready. The protocol adapter adds about 13 MB of service memory,
sharing the same resident Ministral. About 19.5 GiB remains available; service
counters do not include every DSP/kernel allocation. Normal adapter logging is
disabled after QA.

The remaining latency is largely CPU prompt processing. For example, the second
live request reused 1,019 cached tokens but still evaluated 59 new tokens in
1.532 s. With one output token, llama.cpp accounts for almost all work as prompt
evaluation; its near-zero `predicted_ms` is **not** the end-to-end decision time.
Without the optional persisted policy cache, cold requests must process the policy and menu too. This optimization removes
multi-token JSON/reason generation and compacts history; it does not accelerate
the CPU kernels or move Ministral to the NPU.

The initial probe setup omitted the temperature sampler, which permitted a
sampled token to differ from the score winner. The strict check rejected those
responses. Accepted runs use `samplers=["temperature"]`, temperature zero, and
explicit winner equality; initial non-fixed probe files are not accepted results.

Private evidence is under `artifacts/agent-single-token-20260919/`. The
`verify_single_token_agent.py` verifier recomputes scores, checks prompt/history
provenance and matches each code against the actual Unreal dispatch. Unit tests
cover probability bounds, non-action winners, biased/sampled replies, invalid
history, source-field rejection and all action translations. This remains a
small simulated development study, not proof of general autonomous reliability.
The proposed missing-frame and sealant-coverage tools are still future work.

After collecting a private run and its adapter logs/health snapshot, reproduce
the audits with:

```bash
python3 scripts/verify_live_agent.py artifacts/agent-run/process_runtime.json
python3 scripts/verify_inspection_arm.py --runtime artifacts/agent-run/process_runtime.json --output artifacts/agent-run/arm-checks.json
python3 scripts/verify_single_token_agent.py \
  --runtime artifacts/agent-run/process_runtime.json \
  --logs artifacts/agent-run/proxy-logs --health artifacts/agent-run/proxy-health.json \
  --output artifacts/agent-run/token-checks.json
```

The last verifier requires a complete fresh smoke trace and one adapter log per
dispatched action. It is intentionally not an audit of arbitrary canceled or
partially collected interactive sessions.

## Policy cache and tool-time preparation

The normal Ministral EVK stack now prepares an exact static policy prefix before
its one-token adapter reports ready. The private file is
`~/qai-dark-factory/cache/ministral-policy/policy.bin` (about 96 MiB), with a
hash-bound identity and manifest. It binds weights, runtime libraries, launch
arguments, backend environment, rendered template and prompt. Edits invalidate
the cache automatically at restart; no controller training is required.

For an already-running older stack, stop only this project's controller services
before invoking the updated launcher. Do not restart Reason2 or adjacent demos:

```bash
systemctl --user stop dark-factory-edge-agent-single-token dark-factory-edge-agent
bash ~/qai-dark-factory/repo/scripts/model/start_evk_qairt.sh --agent
```

A one-time miss evaluates the policy (about 17 s); a matched cache restores in
about 21 ms, plus manifest hashing. Model loading and weight verification still
occur. `/health` reports `policy_cache.source`, `setup_ms` and
`decision_reused:false`. No action or observation is restored from disk.
The native server may emit a setup token during preparation; it is discarded.

The `--prefill-next-turn` adapter flag, enabled by the normal EVK stack, overlaps a small amount of the
next prompt's work with the already-dispatched robot job. Only the selected
assistant code and the following `Tool result: ` envelope are evaluated; no
unknown status, gate code or timestamp is guessed. A native-slot mutex prevents
preparation from racing the next real request. Exact matching against that full
request determines what computation may be reused. I/M actions need no continued
body turn and skip preparation. Health reports its count, timing and errors.

See [the optimization study](agent_optimization_research.md) for live timing,
rejected compressed prompts/conditional plans/Q8/Vulkan probes, mechanical
overlap constraints and the fine-tuning assessment. These changes retain the
same prompt, unadapted Q4 weights and all 13 unmasked actions.
